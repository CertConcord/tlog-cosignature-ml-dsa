# ML-DSA-87 Transparency Cosignatures — draft 02

Status: experimental extension and proposed C2SP amendment. No C2SP algorithm code or IANA registration is claimed.

## 1. Target and need

The pinned C2SP cosignature editor text defines the selected ML-DSA-44 subtree construction. An issuer or witness policy selecting ML-DSA-87 needs an unambiguous key identifier and explicit negotiation instead of treating another parameter set as that algorithm. ML-DSA-87 is an existing standardized algorithm; this proposal adds no new cryptographic primitive.

The technical change is limited to parameter-set selection, key discovery and interoperable encoding. Issuer admission, quorum, operator independence, retention and document authorization remain external policy.

## 2. Experimental selection

A verifier explicitly selects CERTCONCORD-MLDSA87-SUBTREE-v1 and an externally admitted witness name and ML-DSA-87 public key. The profile cannot be inferred from signature length or a document-supplied key.

Until an upstream discriminator is allocated, the experiment computes a four-byte key hint as the first four bytes of SHA-256 over the following concatenation:

    UTF8("certconcord/tlog-ml-dsa-87/v1\n")
    || UTF8(name + "\n")
    || DER_SubjectPublicKeyInfo(public_key)

The exact LF characters and DER SPKI are part of that input. This experimental key-hint derivation is not the C2SP ML-DSA-44 key identifier and must not be announced as a registered C2SP verification-key type.

The short hint only selects candidates from already trusted keys. It is not a collision-resistant certificate identity or authority decision. The verifier checks the actual name, key, algorithm and complete signature; ambiguous matches cannot silently select a different authority.

The reference assumes the shared native Node `KeyObject` prototypes remain stable during each operation. It captures the native role, algorithm and public export methods when the module loads, isolates the supplied public key's own properties with `structuredClone` before DER export, then reparses that SPKI as the verifier's public key. Own instance properties named `type`, `asymmetricKeyType`, `export` or `context` cannot change a successfully derived algorithm, hint or empty signature context. A later edit to a shared prototype can interrupt DER export or selection; normal completion is not promised under that runtime-wide mutation. A successful DER export still supplies bytes from the native key material for reparsing. A proxy or altered key prototype fails the public-key selection boundary. Direct verification also accepts an ordinary private ML-DSA-87 `KeyObject` by deriving its public key first. The KeyObject-boundary vectors pin the ML-DSA-87 and ML-DSA-44 SPKI hashes, name bytes, four-byte hints, signed input hashes and signature hash, with accepted and rejected shadow cases. This does not change published ML-DSA-44 key identification.

The public key-hint, candidate-selection and direct-verification entry points reject a revoked `KeyObject` proxy before JavaScript's `instanceof` can raise a native `TypeError`. The key-hint and direct-verification entries use `NOTE_KEY_SCHEME`; candidate selection uses `NOTE_KEY_CANDIDATES`. The revoked-KeyObject vectors pin the same admitted ML-DSA-87 SPKI, four-byte hint, 103-byte signed input and 4,627-byte signature for three ordinary successes and three rejected wrappers. This error classification grants no key authority and does not alter ML-DSA-44 identification.

`selectMlDsa87Key` is the reference discovery step after an application explicitly authorizes this experimental profile and supplies at most 64 admitted candidates as public `KeyObject` values. It matches the exact name, actual ML-DSA-87 key type and four hint bytes, rejects duplicate matches, and returns a key for subsequent signature verification. Unrelated candidates may use other UTF-8 names; only the selected name is subject to this profile's ASCII subset. It skips candidates with another algorithm, including ML-DSA-44; it never interprets their C2SP key identifiers as this experimental hint. An unknown or ambiguous hint fails closed, and neither a matching hint nor a matching name admits a new authority.

The reference selector reads each candidate's name and public key once. Checks and the returned key use those captured values, so a changing accessor cannot substitute a different name or key after the hint comparison. The candidate-accessor vectors reference exact admitted SPKI bytes and include both accepted and rejected transitions, including an ML-DSA-44 boundary.

The candidate array itself has at most 64 dense, own data slots. The selector captures those slot values before reading any candidate fields, so a field accessor cannot remove a conflicting candidate, replace a later slot, or append a 65th candidate during selection. Sparse, inherited and accessor slots fail with `NOTE_KEY_CANDIDATES`. The candidate-array vectors freeze the original name, key and hint bytes alongside both accepted and rejected array transitions.

Each candidate record supplies its own `name` and `publicKey` fields. The selector captures ordinary records' data-field values and the four hint bytes before invoking any candidate accessor, so one accessor cannot erase a later ordinary candidate's original name or key. A registry may contain one accessor-bearing candidate; two or more cannot provide a stable cross-candidate snapshot and fail with `NOTE_KEY_CANDIDATES` before any getter runs. Inherited fields and proxy records also fail with `NOTE_KEY_CANDIDATES`. The one accessor-bearing candidate retains sequential first-read behavior: its `name` is read once and, if it matches, its then-current `publicKey` is read once. A present getter is invoked intrinsically with that candidate as its receiver; an absent getter yields an invalid field. This includes a `name` getter that changes its own key before that first key read. The candidate-record vectors freeze exact name, hint and SPKI bytes for both ML-DSA-87 and the skipped ML-DSA-44 boundary.

The selector admits a key hint only as a non-proxy Buffer with intrinsic Uint8Array identity and exactly four native bytes. It copies those bytes before inspecting candidate slots or invoking candidate getters. A shadowed visible `length` or `byteLength` cannot change key selection; shorter or longer native Buffers, proxies and other TypedArrays disguised with Buffer's prototype fail with `NOTE_KEY_ID` before selection. Source bytes must remain stable during this synchronous copy. The key-hint-buffer vectors freeze the exact admitted SPKI and derived hint bytes, plus positive selection and no-selection negative cases. This does not grant authority to a key based on its four-byte hint alone.

## 3. Signature input and checkpoint encoding

Use pure ML-DSA-87 with empty context over the existing subtree input:

    UTF8("subtree/v1\n") || 0x00
    || uint8_length(name) || UTF8(name)
    || uint64_be(timestamp)
    || uint8_length(origin) || UTF8(origin)
    || uint64_be(start) || uint64_be(end)
    || root_hash_32_bytes

Names and origins use the selected printable ASCII subset of the upstream name profile, excluding space, control characters and `+`, and fit their one-byte length. Other upstream UTF-8 names are outside this selected profile. Integer ranges and subtree alignment follow the pinned MTC/C2SP rules. A nonzero timestamp requires a prefix subtree starting at zero. The origin, range, root and witness name are all authenticated. Hashing the message again before a pure-message signing call changes the protocol.

The direct `subtreeInput` encoder requires a non-proxy Buffer root with intrinsic Uint8Array identity and exactly 32 native bytes. It copies those bytes into an owned Buffer before concatenating the signed input, so a shadowed visible `length` or `byteLength` property cannot truncate or extend the authenticated root. Shorter or longer native Buffers, proxies and other TypedArrays disguised with Buffer's prototype fail with `SUBTREE_CONTEXT` before producing a preimage. Source bytes must remain stable during this synchronous copy. The context-root vectors freeze the unchanged complete positive preimage, the deterministic shorter preimage previously produced by a 16-byte root with forged visible length, and exact native bytes and no-preimage results for rejected inputs. This direct encoding gate also applies when verification constructs the expected signed message; it does not by itself authenticate a signature.

The reference encoder accepts exact `BigInt` values across the unsigned 64-bit range and safe JavaScript `number` integers. It rejects unsafe `number` values for start, end and timestamp before conversion, because JavaScript may already have rounded those values and signed different bytes. It also rejects other input types at this direct encoding boundary, including strings, booleans and arrays, rather than coercing them through `BigInt`. The frozen integer-boundary and integer-input-type vectors distinguish accepted bytes from forbidden rounded or coerced bytes. The HTTP request parser separately accepts only canonical unsigned decimal text and passes parsed `BigInt` values to this encoder.

For a checkpoint signed note, the signature payload is key_hint || uint64_be(timestamp) || signature, encoded with canonical padded base64 on the existing witness-signature line. A subtree cosignature is only the raw signature: it has no key hint or timestamp prefix. Its signed input still contains the fixed zero timestamp. Base64url, omitted padding, carriage returns and trailing bytes are not interchangeable encodings.

ML-DSA-87 signatures contain 4627 bytes. The key is supplied as an exact admitted SPKI; a public key with another algorithm is rejected. Reference verification uses Node's cryptographic stack, not a new ML-DSA implementation.

The direct `verifyCosignature` entry admits a signature only as a non-proxy Buffer with intrinsic Uint8Array identity and exactly 4,627 native bytes. It copies those bytes into an owned Buffer before pure ML-DSA-87 verification with empty context. Caller-owned `length` and `byteLength` properties cannot suppress verification of an otherwise valid signature; native short and long Buffers, proxy values and other TypedArrays disguised with Buffer's prototype return `false` before verification. Source bytes must remain stable during the synchronous copy. The signature-verifier vectors freeze the admitted SPKI, complete signed input, exact positive and negative signature bytes and ten boolean outcomes. A successful result still requires the externally admitted key and matching authenticated context; this byte admission does not itself authorize a witness.

## 4. Selected subtree transport

The transport profile is `C2SP-20261007-MLDSA87-v2`, based on editor commit `a29318317776ae8a0e65ff45cfe450fd935a1aca`. This is an explicit experimental selection, not a stable C2SP release or assigned C2SP algorithm. The signing construction and experimental key hint remain `CERTCONCORD-MLDSA87-SUBTREE-v1`; changing carriage does not change the signed message.

`POST /sign-subtree` carries `subtree start end`, one base64 root hash, zero to 63 base64 consistency hashes, an empty line, and a checkpoint. Every line ends in LF. Integers are unsigned 64-bit decimal without leading zeros; hashes are exactly 32 bytes. The requested range must be aligned and end at or before the checkpoint size.

The reference request encoder accepts exact `BigInt`, safe JavaScript `number`, or canonical unsigned decimal `string` values for start and end. It rejects arrays and objects before string conversion, even if their custom string form would be a valid decimal. The request-input-type vectors freeze the full canonical request bytes that such coercions formerly emitted. The parser of received HTTP text continues to accept only canonical decimal fields and returns exact `BigInt` values.

The request encoder requires a non-proxy proof array of at most 63 slots, each containing an own data property whose value is a non-proxy Buffer with intrinsic Uint8Array identity and exactly 32 native bytes. A sparse array is rejected instead of silently omitting a missing hash and emitting a shorter valid request; a changing accessor is rejected instead of emitting a hash length different from the one checked. A proxy array is rejected before the array check because its reported length or slot descriptors can change during validation and silently omit a supplied hash; a revoked proxy also returns `SUBTREE_REQUEST` instead of the prior native `TypeError`. The encoder captures the array length once. For each hash, it checks the intrinsic TypedArray byte length and copies from the source's native bytes into an owned 32-byte Buffer with a captured native `set` method before serializing. Own `length` or `byteLength` properties cannot make a shorter or longer native Buffer pass or change the copied bytes; a proxy Buffer fails at the element boundary. A Uint16Array or Uint32Array with Buffer's prototype is rejected even if `Buffer.isBuffer` returns true: its element-wise copy could change the request hash bytes. Source bytes must remain stable during this synchronous copy. The proof-buffer vectors freeze exact native input bytes, the complete positive request wire, prior element-copy bytes for the rejected typed-array disguises, and expected no-wire negative outcomes. The sparse-proof vectors freeze the full wire bytes for dense zero-, one- and two-hash requests and bytes previously emitted by other rejected inputs. The revoked-array-proxy case records that the old encoder produced no wire and uses the one-hash wire solely as a comparison for its underlying array.

The request root uses the same non-proxy Buffer, intrinsic Uint8Array identity and exact native 32-byte check before consistency input construction and request serialization. The encoder copies its native bytes into an owned Buffer, so a shadowed `length` or `byteLength` property cannot change the root line. A shorter or longer native Buffer, a proxy, or another TypedArray disguised with Buffer's prototype fails with `SUBTREE_REQUEST` before producing a request. Source bytes must remain stable during this synchronous copy. The root-buffer vectors freeze exact native input bytes, the unchanged complete positive request wire and expected no-wire negative outcomes; an older short Buffer copy could include allocator-dependent bytes and is not frozen as a historical output.

The reference transport rejects decimal fields longer than 20 ASCII digits before numeric conversion; an unsigned 64-bit value cannot need more. It also checks the `/sign-subtree` range line against the 49-character maximum for canonical ASCII fields before matching them. A request with at most 63 canonical 44-byte proof hashes has a pre-checkpoint section of at most 2,929 characters; the parser rejects a longer section or more than 64 root-plus-proof lines before decoding any hashes. Before parsing a request checkpoint, it also rejects three or more signature lines, retaining normal duplicate detection for two lines. These limits preserve the accepted wire format while avoiding large-integer conversion and excessive hash or checkpoint-signature decoding on oversized invalid input. The transport-bound vectors specify exact replacement bytes and hashes for accepted, out-of-range and one-million-digit request and checkpoint examples, plus 63, 64 and 10,000 proof-hash lines, 10,000 distinct checkpoint-signature lines, and the exact 2,929-character positive boundary. The checkpoint size examples exercise structural parsing only; changing their size does not preserve their original signature. The synthetic proof-count examples likewise test transport structure, not Merkle consistency.

The request encoder reads the supplied checkpoint property once. Its early three-or-more-signature-line bound and subsequent parser use that same value, so a changing getter cannot substitute another checkpoint between those steps. Exactly two signature lines still reach the parser, retaining duplicate-identity diagnostics. The checkpoint-accessor vectors freeze the complete accepted request and a 188,960-byte, 10,000-signature checkpoint. They cover both first-read orders, including rejection before base64 decoding when the first value has 10,000 signatures.

The submitted checkpoint MUST contain exactly one note signature, from the selected witness key. It MUST NOT include an additional log or witness signature. The service authenticates that checkpoint with the selected witness's key and verifies subtree consistency before signing. The response MUST use the same witness key. Rotation to a different response key is not inferred from a key hint.

The standalone `verifySubtreeCheckpoint` gate rejects a second signature line before decoding any signature payload, even if that extra line is malformed. It still scans the bounded input and validates the checkpoint body and root, but does not decode each invalid extra signature. The generic `parseCheckpointEnvelope` remains able to parse structurally valid multi-signature checkpoints; it does not grant witness authority or replace cryptographic verification.

A successful response is canonical padded base64 of exactly 4,627 raw ML-DSA-87 signature bytes followed by one LF. A signed-note response line, zero timestamp prefix, key-hint prefix, extra line or omitted padding is rejected. Neither a parser nor a length check authenticates a response: the client MUST verify the raw signature over the expected origin, range, root and witness name under its selected public key.

The reference response encoder admits a non-proxy Buffer only when it has intrinsic Uint8Array identity and exactly 4,627 native bytes. It copies those bytes into an owned Buffer before producing the padded base64 line. A shadowed visible `length` or `byteLength` property cannot change the line; shorter or longer native Buffers, proxies and other TypedArrays disguised with Buffer's prototype fail with `SUBTREE_SIGNATURE_LENGTH` before any response is emitted. The source bytes must remain stable during this synchronous copy. Response-buffer vectors freeze the unchanged complete positive line, two deterministic malformed lines previously emitted from short and long native Buffers with forged visible lengths, and exact native bytes and no-wire results for rejected inputs. This admission and encoding rule does not authenticate the signature.

This witness-only request checkpoint is distinct from the published `/checkpoint` object of the tiled log API. A published log checkpoint MUST contain a valid signature from the admitted log and may also contain cosignatures. Applications MUST cryptographically verify that log signature. `assertCheckpointLogSignature` checks only structural presence of an externally supplied name and key hint; it does not establish authenticity, key ownership or log admission.

The structural log-signature presence gate accepts the external key hint only as a non-proxy Buffer with intrinsic Uint8Array identity and exactly four native bytes. It copies those bytes before comparing with the parsed checkpoint signature. An own `length` or `byteLength` property cannot change a successful structural match; native short or long Buffers, proxy values and other TypedArrays disguised with Buffer's prototype fail with `CHECKPOINT_LOG_KEY`. A different valid four-byte hint still fails with `CHECKPOINT_LOG_SIGNATURE_REQUIRED`. Source bytes must remain stable during this synchronous copy. The log-key-ID vectors freeze the complete checkpoint wire and body, its 68-byte log signature payload, admitted log SPKI and key ID bytes, and ten positive and negative structural outcomes. Applications still must verify the log signature cryptographically under their admitted log key.

The selected reference rejects checkpoint extension lines, duplicate name/key-hint pairs and names outside its ASCII subset. It provides bounded encoding and cryptographic checks, not the log's durable consistency state, an HTTP server or a complete Merkle proof implementation. Those obligations remain mandatory for applications using this transport.

## 5. Downgrade and transition

Peers advertise and authorize this experimental profile separately. A peer requiring ML-DSA-87 cannot fall back to ML-DSA-44 or a classical algorithm after an unsupported-profile response.

An eventual upstream-assigned type requires a new explicit adapter and test vectors. Draft 01 subtree HTTP carriage is rejected by this draft; there is no implicit fallback or second runtime. Existing archived checkpoint notes retain their original bytes and experimental key-hint rules. Replacing a key hint in an old note is not a valid migration. Independent adoption does not require any CertConcord governance or signed control object.

## 6. Proposed upstream amendment and limitations

The upstream review question is whether another parameter set belongs in the cosignature registry, and, if so, which discriminator and public-key encoding should be assigned. A proposed registered form should reuse the upstream key-hash layout with its actual assigned type; this experiment intentionally claims no free registry value.

The retained prefix vector covers exact key selection, a prefix subtree and a valid signature. The serialized transport vectors additionally cover the request, checkpoint signatures, raw response, required published log signature and rejected old carriage. Negative cases change origin, range, witness name, root, timestamp, algorithm and signature bytes. They establish encoding and signature semantics, not the necessity of ML-DSA-87, independent operator deployment, or a complete composition security proof. Larger keys and signatures require availability and transport-limit evaluation.

The reviewed editor delta separates checkpoint and subtree cosignature carriage, moves checkpoint key identifiers to the checkpoint specification, requires exactly one witness signature in a subtree request, and requires a log signature on a tiled-log checkpoint. The ML-DSA input structure is unchanged. MTC draft-07 was published on 7 October 2026 and is the selected MTC source. Its assigned certificate OIDs do not alter this component's subtree signature input. C2SP published signed-note, tlog-checkpoint, tlog-cosignature and tlog-witness v1.1.0 on the same date; the release commit b2dd9892338af7009733a4575a6da05811ffae6c changes versioned references relative to the retained a293183 snapshot without changing signature inputs, type bytes or HTTP carriage. The component therefore retains its evaluated source bytes and wire identifier. This component does not implement MTC certificate issuance or path validation.
